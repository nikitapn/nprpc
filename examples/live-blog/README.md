# Live Blog Example

`examples/live-blog` is the unified NPRPC demo workspace built around a simple blog product:

- blog listing and pagination via regular typed RPC calls
- post pages with comments via regular typed RPC calls
- post-specific live chat via bidi streams
- room for later media/video streaming from the same backend contract

The goal is to demonstrate a realistic architecture rather than a toy transport benchmark.

## Architecture

Pages are rendered in the process that owns the data. The Swift backend holds
the repository, so `/blog` and `/post/<slug>` are built from `PostPage` and
`PostDetail` directly — no shell, no skeletons, no hydration round-trip, and no
Node worker in the path.

- `swift/` — Swift backend: the demo services plus `LiveBlogWeb`, the page handler
- `templates/` — Mustache templates, language-neutral and shared with any backend
- `client/` — browser code for the interactive islands (chat, video)
- `cpp/` — C++ backend implementing the same contracts

```text
browser ──HTTP──▶ NPRPC C++ HTTP server
                     ├── /rpc            → RPC dispatch
                     ├── page handler    → Swift: repository → Mustache → HTML
                     └── everything else → static file cache (zero-copy)
```

The page handler is registered with `withPageHandler` and returns `nil` for
anything it does not recognise, so assets keep their zero-copy path:

```swift
let web = try BlogWeb(templateDirectory: "/app/templates", data: repository)

let rpc = try RpcBuilder()
  .withHttp(8443)
    .withPageHandler { web.handle($0) }
    .rootDir(staticRoot)
  .build()
```

`BlogWeb` reads through `BlogDataSource`, which is deliberately the same shape as
`BlogServiceProtocol` — the pages and the RPC endpoint go through one repository,
so they cannot drift apart.

### Islands

Everything that is just content is server HTML. Two things need a live NPRPC
connection and stay in the browser, mounted on the markers `post.mustache`
emits:

- `data-nprpc-chat` — `JoinPostChat` bidi stream
- `data-nprpc-video` — `OpenPostVideo` server stream, fed into a MediaSource

`client/` is plain TypeScript built by Vite into a single `islands.js` — no
router, no SSR, no component framework, because there is no page state to
manage. Each island builds its own DOM and `mountAll` skips elements it has
already claimed, so the bundle re-mounts safely after an htmx swap.

Without JavaScript the `<noscript>` text in each marker is what stays on the
page; the rest of the post renders regardless.

### htmx

Pagination and comment loading go through htmx. A route renders the full page
normally and the partial alone when the request carries `HX-Request: true`, so
`partials/post_cards.mustache` is both part of the page and the fragment that
replaces it — one template, no second rendering path in the browser.

### Templates

Template names are paths below `templates/` without the extension, so
`partials/post_cards.mustache` is `{{> partials/post_cards}}`.

The npidl-generated Swift structs work as template contexts directly —
swift-mustache resolves fields by reflecting over stored properties and unwraps
Optionals, so `cover_url: String?` drives `{{#cover_url}}...{{/cover_url}}` with
no mapping code. `Sources/LiveBlogWeb/ViewModels.swift` wraps them only where a
template needs something the contract does not carry, such as a formatted date
or a link, and stores it: a computed property is invisible to reflection.

Set `LIVE_BLOG_TEMPLATE_RELOAD=1` to re-read templates on every render, and
`LIVE_BLOG_TEMPLATES` to point somewhere other than `/app/templates`.

## Planned Feature Coverage

### Blog

- `listPosts(page, pageSize)`
- `getPost(slug)`
- `listComments(postId, page)`
- `getAuthor(slug)`

### Chat

- `joinPostChat(postId)` using a bidi stream
- client sends messages upstream
- server pushes chat messages, join/leave events, and moderation events downstream

### Media Later

- server stream for post-attached video or audio
- same Swift server, same typed contracts, different interaction mode

## Folder Layout

```text
examples/live-blog/
├── README.md
├── templates/  # Mustache page templates, shared by any backend
├── web/        # Tailwind source + vendored htmx
├── client/     # browser islands (chat, video)
├── swift/      # Swift NPRPC backend + page handler
└── cpp/        # C++ NPRPC backend using the same contracts
```

## Client Notes

```text
client/src/
├── islands/
│   ├── main.ts     # entry: mounts both islands, re-mounts after htmx swaps
│   ├── chat.ts     # ChatService.JoinPostChat
│   ├── video.ts    # MediaService.OpenPostVideo + MediaSource
│   └── dom.ts      # element helpers
├── lib/live-blog-rpc.ts   # chat + media service accessors
└── rpc/live_blog.ts       # generated by npidl
```

`npm run check` type-checks. `noUnusedLocals` is deliberately off in
`tsconfig.json` because `src/rpc` is generated and would trip it on every
regeneration.

## Server Notes

The server side includes:

- a Swift package under `swift/` — services plus the `LiveBlogWeb` page handler
- a native C++ server under `cpp/`

The C++ server implements the same contracts. It does not render pages yet; the
templates are plain text and portable, so a C++ page handler would use
`third_party/Mustache` against the same files.

## Building

```bash
# 1. Generate stubs from the IDL
python3 scripts/gen_stubs.py

# 2. Build islands + CSS, copy vendored assets into the static root
./scripts/build-assets.sh          # add --watch while editing templates

# 3. Build and run the Swift backend
./scripts/build-swift-server.sh
./scripts/run-swift-server.sh
```

`build-assets.sh` assembles `client/build/client/` — gitignored build output —
and leaves the server-generated `host.json` there alone:

- `client/src/islands/` — built by Vite into `islands.js`
- `web/styles/app.css` — Tailwind entry point. `@source` names the templates,
  the islands and the view models, so every place a class name can appear is
  scanned. A class Tailwind misses fails silently as unstyled markup.
- `web/vendor/htmx.min.js` — htmx 2.0.10, vendored and committed.

No framework and no Node in the serving path; this is a build-time step only.

The Tailwind CLI is hoisted to the monorepo root by npm workspaces. If it is
missing:

```bash
npm install -w examples/live-blog/client
```
